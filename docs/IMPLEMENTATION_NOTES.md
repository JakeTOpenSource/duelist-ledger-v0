# Implementation notes (Track B, contract v0.1)

This build targets **contract v0.1**: `BUILD_SPEC.md` at tag `contract-v0.1`, commit `aa4b65c226d7d810492c503c1d307ade787cdc0d` (sha256 `cb50dfa3…fd69ac1e`). The v0 build was written blind from contract v0 (commit `09d26a64`). This v0.1 update was also written blind, on Opus 5.5 (`claude-opus-5-5`).

Part 1 lists every reading the v0 build recorded, with its status under v0.1:

- **kept**: v0.1 is still silent, and the reading is unchanged.
- **pinned by v0.1**: v0.1's text now fixes the point, and the build matches that text.
- **changed by v0.1**: v0.1's text differs from the v0 reading. The entry says what changed.
- **re-read**: the contract text did not change, but the reading was checked against the spec text again for v0.1 and corrected.

Part 2 lists the new ambiguities this build hit under v0.1. Each one says which reading was chosen.

## Part 2: new ambiguities hit under v0.1

v0.1 aims for zero, so each is listed with the clause and the reading chosen.

| # | spec section | ambiguity | reading chosen |
|---|---|---|---|
| N1 | 5.1 | **The order of the groups.** The spec says the groups are "settled group by group, in the rule-table order of each group's first reason", then lists 1. S0, 2. session, 3. action. The Track B prompt's change summary says "S0, then session, then action". The two readings differ whenever an action reason comes first in rule order: H1 or H2 ahead of S0, or H1–H5_BUDGET ahead of a session reason (e.g. the sec. 17 case H5_BUDGET + H5_BUDGET_SESSION). | The spec sentence: rule-table order of each group's first reason. The numbered list is read as the per-group handling. So the HOLD decide() raises always belongs to the first group, and its primary is that group's first reason. In the sec. 17 case, the principal settles H5_BUDGET first, then a follow-on HOLD H5_BUDGET_SESSION goes to `session_holds`. `holds` = [H5_BUDGET, H5_BUDGET_SESSION] and `scopes` = [L3, L1]. The fixed order would give [H5_BUDGET] alone with the default close. |
| N2 | 5.1, 14 | The fields of a follow-on HOLD | Primary = the remaining group's first reason in rule order. Reasons = that group's codes. Scope level = that reason's scope (session group L1, S0 group the held scope's level, action group L0, or L3 for H5_BUDGET). The HOLD decide() raised keeps all the decision's reasons. |
| N3 | 5.6 | The case of a follow-on HOLD | Its pre-class uses the decision-level `failing_tainted` and cited origins, since sec. 4 defines them once per decision and sec. 5.6 says failing_tainted "may come from a non-primary reason". So a follow-on H5_BUDGET_SESSION HOLD after a repinned tainted H4 is injection-suspected, not budget. |
| N4 | 5.1, 6 | Principal matching and options inside a multi-reason action group | Approve rules are matched against the group's first reason (the primary of the HOLD being settled). approve_once is withheld if the group holds H3 or H4 and the decision's failing_tainted is true. repin is offered only if every reason in the group offers it (H3/H4/H8), and it repins the group's first slot-naming reason's slot. |
| N5 | 5.5 | Probe counting for a HOLD the principal never saw | A HOLD whose action is denied by the S0 group (its primary may be H1/H2) does not count, because it was not "denied by the principal". The "primary reason" for counting is the primary of the HOLD the principal actually denied: the action group's HOLD. |
| N6 | 8 | A fault with a missing or non-integer `index` | Missing → 1 (the first occurrence). A non-integer (e.g. `"1"`, `1.5`, `true`) is a load error, like k < 1. An integral float such as `1.0` is accepted as 1. |
| N7 | 4 | "the first guarded slot of the proposal whose value is not pinned anywhere in the declaration" | The tool's guarded slots, in `sinks.json` order, that are present in the proposal's args. "Pinned anywhere" = the value is in any step's pinned list, for any slot. Numbers compare by value (250 = 250.0 = "250"). |
| N8 | 5.6 | Rule 8 "H2 with no failing_slot" when a later reason names a slot | Read as the H2 reason itself naming no slot, per the parenthetical "(every guarded value is pinned somewhere in the declaration…)". So [H2 (all pinned), H3 on `to`] is declaration-gap (when failing_tainted is false), even though the decision's failing_slot is `to`. |
| N9 | 4, 5 | Token expiry for an item held at release that later clears | The spec gives `expires_t` no value and no rule. The build's expiry (mint time + 2 × the largest window) is not enforced on an item the gate itself held at an earlier release pass. Otherwise a link that clears late (SEQ_GAP is the only clearable link in v0.x) would turn a benign release into a T4 TRIP. |
| N10 | 14 | `detected` with several faults, or a fault that never fires | Per fault. drop_receipt → a RECEIPT_GAP for the effect whose receipt that fault dropped. bypass_write → a T3_BYPASS for that fault's effect. A tamper → the tamper was applied and CHAIN was raised. mutate_escrow → a T4 on the item that fault mutated. A fault that never fires (e.g. a mutate_escrow index beyond the escrowed items, or any mutate_escrow in A0/A3) produced no signal, so `detected` is false. |
| N11 | 8 | mutate_escrow on a sink with no dest_slot (persist_memory) | The first guarded slot (`key`) is used. The slot is written even if the proposal lacked it. |
| N12 | 5.6 | Cited origins of an H7 case | An injection-suspected H7 cites no origins (there is no failing arg, and it is not T1/T2), so it never feeds common-mode. |
| N13 | 5, 9 | Where the SESSION_OPEN verify failure is logged | ALARM, HOLD CHAIN and its CASE are logged before the SESSION_OPEN entry, tagged with the new session's id. Then SESSION_OPEN and SESSION_CLOSE REFUSED follow. `holds` gets CHAIN (L3), `pre_classes` gets sensor-fault, and `outcomes` gets REFUSED for that session. |
| N14 | 5.5 | An A7 DENY whose primary is not a probe code (e.g. S0 + a tainted H4) | "every A7 DENY" counts, whatever its primary. |
| N15 | 14 | Expectations whose `version` is not "0.1" | Still compared. The report and console carry a note naming the version. |
